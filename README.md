## מבוא

המערכת מיועדת לתמוך בתהליך העבודה של מחלקת מעבדה בבית חולים: רופא מזמין בדיקות עבור מטופל, ההזמנה מתפרטת לבדיקות מעבדה מסוגים שונים, ועובדי המעבדה מבצעים את הבדיקות ומדווחים תוצאות. תוצאות שסומנו כחריגות עשויות להפיק התראות, שניתן לעקוב אחר חומרתן ומצב הטיפול בהן.

נשמרים פרטי זיהוי וקשר של מטופלים ורופאים, קטלוג סוגי בדיקות, פרטי עובדי מעבדה, הזמנות, בדיקות, תוצאות והתראות. ההפרדה בין הזמנה, מופע בדיקה וסוג בדיקה מאפשרת להזמין כמה בדיקות באותה הזמנה ולהשתמש באותו סוג בדיקה בהזמנות רבות. שמות המטופל והרופא נשלפים דרך הקשרים ואינם מועתקים לתוצאות ולהתראות.

כל הנתונים ששימשו בפרויקט הם נתוני דמה לצורך לימודי. סימון החריגות נוצר באופן סינתטי לצורך בדיקת התהליכים; אין בסכמה טבלת טווחי ייחוס, ולכן המערכת אינה מחשבת כאן החלטות קליניות או טווחים רפואיים.

### הישויות והקשרים

| ישות | תפקיד | מפתח ראשי | קשרים עיקריים |
|---|---|---|---|
| PATIENT | פרטי מטופל | PatientID | מטופל אחד להזמנות רבות |
| DOCTOR | הרופא המזמין | DoctorID | רופא אחד להזמנות רבות |
| TESTTYPE | קטלוג סוגי בדיקות | TestTypeID | סוג אחד למופעי בדיקה רבים |
| LABTECHNICIAN | עובד מעבדה והסמכה | TechnicianID | עובד אחד לבדיקות רבות; השיוך לבדיקה אופציונלי |
| TESTORDER | הזמנת בדיקות | OrderID | מטופל אחד, רופא אחד ובדיקות רבות |
| LABTEST | מופע בדיקה בהזמנה | LabTestID | הזמנה אחת, סוג אחד, עובד אופציונלי ותוצאה אופציונלית יחידה |
| TESTRESULT | תוצאת בדיקה | ResultID | בדיקה אחת בדיוק; התראות רבות אפשריות |
| LABALERT | התראה על תוצאה | AlertID | תוצאה אחת בדיוק לכל התראה |

מפתחות הזרים המחייבים מוגדרים NOT NULL. השדה TechnicianID ב־LABTEST נשאר nullable בהתאם לסימון האופציונלי ב־DSD. UNIQUE על TESTRESULT.LabTestID אוכף לכל היותר תוצאה אחת לבדיקה. אין UNIQUE על LABALERT.ResultID, ולכן ניתן לשמור כמה התראות לאותה תוצאה. כל מפתחות הזרים משתמשים ב־NO ACTION, ללא מחיקת ילדים אוטומטית.

הזמנה רשאית להכיל כמה בדיקות. LABTEST מקשרת בין הזמנה לבין סוג בדיקה באמצעות מזהה עצמאי ומחזיקה גם מידע על ביצוע. לכן אותו סוג בדיקה רשאי להופיע שוב באותה הזמנה; לא נוסף אילוץ UNIQUE על הזוג OrderID, TestTypeID שלא הופיע בתכנון.

בסכמה יש DATE אחד: DateOfBirth. מועדי ההזמנה, הבדיקה, התוצאה וההתראה הם TIMESTAMP ושומרים גם שעה. לפי הוראת המגישות נשמרו התרשימים והטיפוסים המאושרים ולא בוצעה המרה שמאבדת שעות. דרישת המרצה המילולית לשני שדות DATE עדיין דורשת הבהרה מול האישור שניתן לתכנון; אין לסמן אותה כמתקיימת מילולית.

## נרמול ותלויות פונקציונליות

הניתוח מבוסס על התלויות העסקיות של התכנון המאושר, ולא על מקריות בנתוני הדמה. בכל טבלה המפתח הראשי קובע את כל שאר שדותיה. נוסף על כך, מפתחות המועמד הבאים קובעים את שאר שדות הטבלה:

| טבלה | מפתחות מועמד ותלויות |
|---|---|
| PATIENT | PatientID → שאר השדות; IDNumber → שאר השדות |
| DOCTOR | DoctorID → שאר השדות; LicenseNumber → שאר השדות |
| TESTTYPE | TestTypeID → שאר השדות; TestCode → שאר השדות |
| LABTECHNICIAN | TechnicianID → שאר השדות; CertificationNumber → שאר השדות |
| TESTORDER | OrderID → OrderedAt, Priority, Notes, PatientID, DoctorID |
| LABTEST | LabTestID → Status, PerformedLocation, ScheduledAt, StartedAt, CompletedAt, OrderID, TestTypeID, TechnicianID |
| TESTRESULT | ResultID → שאר השדות; LabTestID → שאר השדות בזכות UNIQUE NOT NULL |
| LABALERT | AlertID → Severity, Message, CreatedAt, Status, AcknowledgedAt, ResultID |

**1NF:** בכל שדה נשמר ערך יחיד, ואין רשימת בדיקות בתוך שדה של הזמנה. כל בדיקה נשמרת כרשומה נפרדת ב־LABTEST. הערות וטקסט תוצאה הם ערכים טקסטואליים יחידים מבחינת מודל המערכת.

**2NF:** כל מפתחות המועמד המתועדים הם חד־שדהיים, ולכן אין תלות של תכונה רק בחלק של מפתח מורכב.

**3NF:** לפי התלויות העסקיות של המודל אין תלות לא־טריוויאלית בין שדות שאינם מפתח באותה טבלה. פרטי מטופל ורופא נשמרים רק בישויות שלהם; קטלוג בדיקה נפרד ממופע בדיקה; פרטי עובד נפרדים מתהליך הביצוע. כך שינוי טלפון של רופא אינו דורש עדכון בכל הזמנה, ושינוי שם בדיקה אינו מחייב שינוי בכל תוצאה.

Unit בתוצאה היא היחידה שבה התוצאה דווחה בפועל, בעוד DefaultUnit היא ברירת מחדל בקטלוג. אין הנחה שיחידת כל תוצאה חייבת תמיד להשתוות לברירת המחדל, ולכן אין להסיק תלות TestTypeID → Unit בטבלת התוצאות. באופן דומה שם בדיקה אינו מוגדר ייחודי ואין להניח שהוא קובע קטגוריה; IsAbnormal אינו מחושב מ־NumericValue בלבד משום שהקשר הבדיקה קובע את המשמעות. בהנחות אלה הסכמה מקיימת 3NF. הוספת כללים עסקיים חדשים עשויה לדרוש בחינה מחודשת, ולא בוצעה במסגרת המבנה המאושר.

## יצירת בסיס הנתונים

סביבת הפרויקט הקיימת כוללת Docker Compose, PostgreSQL 16 ו־pgAdmin 4. שם מכולת PostgreSQL הוא `postgres_db`, ושם מכולת pgAdmin הוא `pgadmin_ui`. החיבור ב־pgAdmin נקרא `Hospital_Lab`.

**שם בסיס הנתונים בפועל הוא `Hospiatl_Lab_db`**, כולל שגיאת האיות הקיימת. השם אומת מול השרת; הוא לא שונה כדי לא לפגוע בחיבורים הקיימים. PostgreSQL שנבדק דיווח על גרסה 16.15.

ארבעת קובצי ההגשה המקוריים היו ריקים בדיסק אך כללו עריכות פתוחות ב־VS Code. התוכן שוחזר מגיבויי העריכה ונשמר בתיקיית ההגשה, בלי לדרוס את העריכות הפתוחות. קובצי הסכמה הישנים `01-schema.sql` ו־`seed-data.sql` השתייכו לתכנון מוקדם אחר ואינם קובצי ההרצה של ההגשה הנוכחית.

## הוראות הרצה

הקבצים מתאימים ל־PostgreSQL 16. אפשר להשתמש ב־psql מותקן או ב־psql שבתוך מכולת PostgreSQL. יש לעבוד על בסיס חדש וריק, ולא להריץ אכלוס מחדש בבסיס הראשי. הסקריפטים מכניסים מזהים קבועים בכוונה, והרצה כפולה נכשלת במקום לדרוס רשומות.

### הקמה באמצעות psql

מתוך תיקיית `שלב א`, כאשר פרטי החיבור מוגדרים במחשב המקומי:

```powershell
createdb -U YOUR_LOCAL_USER stage_a_submission
psql -U YOUR_LOCAL_USER -d stage_a_submission -v ON_ERROR_STOP=1 -f createTables.sql
psql -U YOUR_LOCAL_USER -d stage_a_submission -v ON_ERROR_STOP=1 -f insertTables.sql
psql -U YOUR_LOCAL_USER -d stage_a_submission -v ON_ERROR_STOP=1 -f selectAll.sql
```

`insertTables.sql` הוא סקריפט psql, ומשתמש ב־`\ir`, ב־`\cd` וב־`\copy`. אין להדביק אותו בשלמותו לעורך השאילתות של pgAdmin, שאינו מפרש פקודות psql. קובצי createTables.sql, extendCatalog.sql, baseSeed.sql ו־generated.sql הם SQL רגיל. לצורך ייבוא CSV ב־pgAdmin ניתן לבחור Import/Export על LABTECHNICIAN, לציין CSV עם Header ולהתאים את חמש העמודות לפי סדרן; התהליך המתועד בפרויקט נעשה בפועל דרך psql.

### יצירה חוזרת של פלט Python

```powershell
python Programing/generate_data.py
```

יש לשמור את `orders.csv` לצד התוכנית. הפקודה יוצרת מחדש את generated.sql בלבד; היא אינה מתחברת לבסיס הנתונים ואינה מכניסה נתונים עד שהפלט מורץ בנפרד. בסביבה שבה אין Python ב־Windows אפשר להשתמש ב־Python שכבר קיים במכולת pgAdmin, כפי שנעשה במהלך הפרויקט.

### הרצה ב־Docker הקיים

יש להעתיק את תיקיית `שלב א` אל מכולת PostgreSQL, למשל ל־`/tmp/stage_a_submission`, ואז להריץ את psql משם. בתוך המכולה אפשר להשתמש ב־POSTGRES_USER המוגדר בסביבה, בלי להציג סיסמאות:

```sh
createdb -U "$POSTGRES_USER" stage_a_submission
cd /tmp/stage_a_submission
psql -U "$POSTGRES_USER" -d stage_a_submission -v ON_ERROR_STOP=1 -f createTables.sql

```

לשחזור גיבוי Custom משתמשים ב־pg_restore, ולא בפתיחת קובץ הגיבוי בעורך SQL. אין צורך להריץ createTables.sql לפני שחזור גיבוי מלא, משום שהגיבוי כולל גם סכמה וגם נתונים.
